\begin{abstract}
We reverse engineered the high-level design of WolfBite, a Flutter/Firebase
WIC shopping assistant, using multiple large language models and direct
repository evidence. We designed and executed tests against the resulting use
cases, traced those tests to the design, and assessed the inherited suite only
after completing the independent design pass. The curated suite executed 123
tests: 112 passed, three exposed unhandled or misleading user paths, one
exposed a test-scope mismatch, and seven encountered the same Flutter
shader-renderer failure. This report presents those findings without repairing
the inherited application.
\end{abstract}

\section{Product Choice (D1)}

\textbf{Product:} WolfBite.\\
\textbf{Original repository:}
\url{https://github.com/SuyeshJadhav/CSC510_G19}.\\
\textbf{Team fork:}
\url{https://github.com/closeabigaile/SEf26_project}.\\
\textbf{Production baseline commit:} \texttt{cc22b3c}.\\
\textbf{Curated-suite commit:} \texttt{8461250}.

We selected WolfBite because it is a user-facing Flutter application with
several interconnected features, including authentication, barcode and receipt
scanning, persistent basket state, WIC benefit limits, and nutritional
calculations. These interactions provide meaningful state transitions, edge
cases, and testing opportunities. The application could still be built and
launched, although parts of its inherited test suite showed dependency rot and
some features appeared incomplete or insufficiently defined. We did not
evaluate and abandon another project before selecting WolfBite.

\subsection{Build and Execution Baseline}

The inherited web application built and displayed its sign-in page. During the
initial test run, 22 tests passed, while five test files did not compile because
fresh dependency resolution selected incompatible Firestore and fake-Firestore
interfaces. We classified this as dependency/code rot and did not repair it.
Git history on \texttt{main} contains separate Project 1a commits from all four
authors and merge commits for each assigned use-case range.

\section{Reverse-Engineered Use Cases (D2)}

The final use cases reconcile Codex, Gemini, GPT-5.6-terra, and a limited local
Llama review. Repository evidence settled disagreements: barcode and manual UPC
entry were combined as one identification goal; monthly reset remains an
extension of session restoration; direct lookup is not described as guaranteed
WIC verification; receipt import is distinct from checkout; and QR preparation
is distinct from finishing the local shopping session.

\subsection{UC1: Create account}
\ucfield{Primary actor}{New shopper}
\ucfield{Stakeholders and interests}{Shopper: obtain a usable account and retain profile information. Service owner: maintain valid, attributable accounts.}
\ucfield{Preconditions}{Shopper is signed out and account services are available.}
\ucfield{Trigger}{Shopper chooses to create an account.}
\ucfield{Main success scenario}{1. Shopper provides the required account and profile information. 2. System validates the information. 3. System creates the shopper's account. 4. System saves the shopper's profile. 5. System ends the initial session and makes sign-in available.}
\ucfield{Extensions}{2a. Required information is blank or invalid: system identifies the invalid entry and does not submit. 3a. Account creation is rejected: system reports the failure and keeps account creation available. 4a. Account creation succeeds but profile saving fails: the account and profile are left incomplete, with no reliable recovery in this flow.}
\ucfield{Postconditions}{The account and profile exist, and the shopper can sign in.}

\subsection{UC2: Sign in}
\ucfield{Primary actor}{Returning shopper}
\ucfield{Stakeholders and interests}{Shopper: gain secure access to saved shopping information. Service owner: reject invalid credentials and protect account data.}
\ucfield{Preconditions}{Shopper is signed out and has an account.}
\ucfield{Trigger}{Shopper chooses to sign in.}
\ucfield{Main success scenario}{1. Shopper provides account credentials. 2. System validates the credentials. 3. System authenticates the shopper. 4. System makes protected shopping features available.}

\ucfield{Postconditions}{Shopper is authenticated and can access protected shopping features.}

\subsection{Errors Caught}

\begin{itemize}
  \item \textbf{Codex Sol:} initially allowed the domain label
  \emph{approved} to imply guaranteed WIC eligibility. Inspection of
  \path{AplService.findByUpc} showed that any matching document is returned;
  only substitute lookup filters \path{eligible}. Code/route inventory also
  disproved README order tracking and separated receipt recognition, Add All,
  QR handoff, and local session completion.
  \item \textbf{GPT-5.6-terra:} promoted category-cap checking and
  \emph{complete transaction} to actor goals, stated persistence too strongly,
  and applied a basket/usage equality invariant after checkout. The state code
  showed that capacity is subordinate to add/review flows, saves are often
  unawaited, and post-checkout usage intentionally remains while the basket is
  empty.
  \item \textbf{Gemini:} claimed signup enters the app, an alternative is
  atomically swapped, direct lookup verifies WIC eligibility, and checkout is
  permanently committed. The signup, scan, APL, QR, and state paths instead
  show sign-out-to-login, additive selection, unfiltered direct lookup, and no
  cashier acknowledgement. Its K4 receipt verdict also contradicted its own
  explanation and was corrected to partial/misleading.
  \item \textbf{Local Llama 3 8B:} fabricated file-line citations, turned
  private persistence/notification helpers into user goals, and inferred QR
  implementation from the dependency list. Manual comparison against the
  cited files found no grounding, so none of its unique claims entered D2
  without independent verification.
\end{itemize}

\subsection{Prompt Utility}

The team used four keeper prompts: K1
evidence-ranked actor goals, K2 state-transition/invariant audit, K3 hostile
boundary miner, and K4 contradiction adjudicator. K1 earned its keep by
forcing exactly 20 ranked, cited goals; K2 exposed paid overflow, unawaited
persistence, and receipt/checkout separation; K3 produced the best nontrivial
test boundaries; and K4 most directly caught stale prose and CI claims. The
generic starter first-contact prompt did not earn a place in final evidence
beyond orientation, and the fragility prompt produced prioritization
hypotheses rather than proof of failure. Local K1, K3, and K4 outputs were not
useful because they lacked repository grounding; local K2's explicit N/A
answers were useful as an honesty check.

\subsection{Model-Specific Strengths and Weaknesses}

\begin{itemize}
  \item \textbf{Codex Sol} connected Flutter UI, state, Firestore, routes,
  workflow, and history into testable invariants; first-pass summaries could
  still over-trust domain labels or promote system behavior into user goals.
  \item \textbf{GPT-5.6-terra} most consistently distinguished evidence from
  inference and found silent failures; its wording still inherited
  \emph{eligibility} and \emph{transaction}, and its OpenAI/Codex lineage
  limits independence from Sol.
  \item \textbf{Gemini} quickly produced a broad, independent inventory of
  visible behavior; it regularly promoted UI labels and README prose into
  stronger guarantees than the code supports.
  \item \textbf{Local Llama 3 8B} followed fixed output formats reasonably
  well; with only manually pasted README and \path{app_state.dart} context, it
  substituted plausible guesses and fabricated citations for repository
  evidence.
\end{itemize}

\subsection{Local Model}

All four keeper prompts were attempted with Llama 3 8B through Ollama. The
runner could not browse the repository, so only README and
\path{app_state.dart} were pasted. K2 honestly marked two missing-context flows
N/A; K1 fabricated citations, K3 supplied 25 uncited generic boundaries, and
K4 reasoned from dependencies rather than production code. The local output
was retained as comparison evidence but not trusted without source
verification.

\section{Conclusion}

The curated suite reaches 84.1\% executable-line coverage and exercises the
main outcomes of 18 of 20 use cases, but its more important result is three
honest user-facing mismatches, one test-scope mismatch, and the quantified
weakness in exception (36.8\%) and persistence (43.5\%) paths. The inherited
suite is strongest in authentication UI and basic balances, while receipt
processing, restoration, paid overflow, error handling, and checkout semantics
remain its largest blind spots. Cross-model checking prevented README claims
and domain labels from becoming false requirements.
